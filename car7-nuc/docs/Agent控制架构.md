# Agent 驱动的机器人控制架构

本文说明一种控制方式：不把交互和编排写进 GUI / 状态机 / 语音框架，而是把顶层功能做成可执行技能，把用法和原则写成文档，再让命令行 Agent（Droid、Codex、Claude Code、Cursor Agent 等）直接负责听懂人话、选技能、执行、回报。

当前 `campusCar-new-chassis` 仓库已经具备这种架构的雏形。本文把它显式化，并给出建议做法和延迟优化。

## 1. 思想

传统做法是：先设计交互（按钮、语音槽位、UE 指令表），再设计控制逻辑（谁先启动、失败怎么回退、用户说“往前一点”对应什么），最后把两者写进代码。每加一种说法、一种任务、一种异常，都要改程序。

这里反过来：

1. **功能是代码，但只做成顶层技能。**  
   每个技能是一个非交互、可重复执行的入口：`.sh`、一条明确的 Python 命令，或一个已存在的 ROS 启动流程。技能负责把车真正开动、探测、停掉、检查、推流。
2. **说明是文档，不是程序。**  
   每个技能配一张短说明书：什么时候用、前置条件、怎么调用、成功长什么样、失败看什么、有哪些安全红线。另外再写交互原则、文档怎么读、当前车处于什么状态。
3. **Agent 是操作员，不是控制器。**  
   人用自然语言说话。Agent 读文档、看现场状态、选技能、跑命令、把结果说给人听。闭环运动、急停、看门狗仍由脚本和硬件负责，不经过大模型。

一句话：人负责意图，文档负责可判定的知识，脚本负责确定性动作，Agent 负责把这三层接起来。省掉的是“再写一套交互和控制编排代码”。

这不是让大模型去发 `/cmd_vel`。那是实时控制，延迟和可靠性都不合格。Agent 只做**任务级**决策：启动全栈、检查健康、开始录路径、切到键盘、停掉相机、解释现在为什么不能走。

## 2. 为什么适合这个项目

这个仓库的工作对象本来就是“一堆已经能跑的顶层动作”，而不是还缺底层驱动：

- 全栈启停、健康检查、键盘控制、Docker 进入、底盘/相机探测，都已经是脚本。
- 操作说明已经写成 `docs/`，不是散落在聊天记录里。
- Agent 启动约定已经写成 `AGENTS.md` / `CLAUDE.md`，项目记忆在 `.codex-memory/`。
- 脚本规范已经要求：默认非交互、可重复执行、失败可从日志判断。

也就是说，交互层一直是“人读文档、人敲脚本”。把这个人换成命令行 Agent，不需要先发明新的控制协议。

适合交给 Agent 的，是低频、允许数秒延迟、需要理解现场的事情：

- “把车拉起来”
- “相机有没有画面”
- “现在能不能给 UE 用”
- “串口又不在了，按文档排一下”
- “录一条路径再停掉”

不适合交给 Agent 的，是高频、必须确定的事情：

- 10 Hz 的速度环
- 松开按键立刻停车
- 硬件急停
- 看门狗超时清零

## 3. 当前环境怎么解读

这次对话所在的工作区，本身就是这套架构的一个运行实例，不是另起炉灶的空仓库。

### 3.1 三层已经在了

| 层 | 这个仓库里是什么 | 对 Agent 的意义 |
|---|---|---|
| 技能 | `scripts/launch_all.sh`、`stop_all.sh`、`check_all.sh`、`stm32_hoverboard_probe.sh`、`hikrobot_camera_probe.sh`、`keyboard_control.sh`、`docker_run_stm32.sh` 等 | 可直接执行的顶层动作 |
| 文档 | `docs/快速启动指南.md`、`docs/部署调试备忘.md`、`docs/UE对接文档.md`、`docs/Docker部署指南.md` | 人/Agent 共用的操作知识 |
| Agent 约定 | `AGENTS.md`、`CLAUDE.md`、`.codex-memory/`、`.github/instructions/` | 告诉 Agent 先读什么、用哪份文档、别走旧底盘 |

`.codex-memory/` 已经按“稳的放 overview、活的放 current-context、过程放 session-log、硬件细节放 systems/”拆开。这就是给 Agent 用的工作记忆，不必再造一套数据库。

### 3.2 运行现场

当前 NUC 上的典型路径是：

1. 主机进入 STM32 Docker：`./scripts/docker_run_stm32.sh`
2. 容器工作目录是 `/workspace/campusCar-new-chassis`（主机仓库挂进去）
3. 容器内再跑 `./scripts/launch_all.sh`

一次已经观察到的启动结果包括：profile `stm32_hoverboard_4wd`、前后串口检查通过、本地底盘驱动在线、`/cmd_vel` 在线、Hikrobot 相机启动命令已发出、RTSP/HLS 地址已打印。也就是说，**技能已经在跑，Agent 缺的是一份“技能目录 + 现场状态 + 决策原则”，不是再写启动逻辑。**

注意路径别名：记忆和文档里的规范根目录是 `~/campusCar-new-chassis`；这台机器上当前仓库也可能以 `~/campusCar` 出现，Docker 内则是 `/workspace/campusCar-new-chassis`。Agent 应以当前工作目录和 `config/robot.env` 为准，不要死记一台机器上的绝对路径。

### 3.3 现在还缺什么

现有材料对“人来操作”已经够用，对“Agent 当主交互”还偏散：

- 没有一份技能目录。Agent 每次都要扫 `scripts/` 和长文档，才能知道能干什么。
- 技能和文档是多对多。`launch_all.sh` 的用法散落在快速启动指南、部署备忘、Docker 指南里。
- 没有“若出现这种情况就执行这个技能”的短剧本，Agent 会现场推理。
- 没有给 Agent 读的短状态快照。它往往用 `check_all.sh`、扫日志、问人来拼出现场。
- 安全边界还写在人看的注意事项里，没有写成 Agent 不可违反的硬规则。

后面的建议就是补这几块，而不是替换现有脚本。

## 4. 建议的分层

```text
人（语音/键盘/聊天）
        │
        ▼
命令行 Agent（理解意图、选技能、解释结果）
        │  只调用目录里的技能
        ▼
技能层（scripts/*.sh 以及少数固定 Python 入口）
        │  确定性、非交互、可重复
        ▼
运行时（ROS2、底盘驱动、相机、推流、UE bridge）
        │
        ▼
硬件（STM32 UART、Hikrobot、RTK、急停）
```

再加两条旁路，不要让它们经过 Agent：

- **实时控制旁路：** GUI / 键盘 / UE `/U2RTopic_Command` 继续直接打到 `/cmd_vel` 或现有 bridge。
- **安全旁路：** 硬件切断 TTL、脚本里的零速停机、进程清理。Agent 可以触发 `stop_all.sh`，但不能当唯一急停。

Agent 的职责边界：

| 做 | 不做 |
|---|---|
| 把“把车开起来”映射到 `launch_all.sh` | 自己拼 `ros2 topic pub /cmd_vel ...` |
| 按剧本先 probe 再 launch | 在对话里发明新的启动顺序 |
| 读 `check_all.sh` 输出并对照文档解释 | 用推理代替健康检查 |
| 组合已有技能：probe → launch → check | 把导航闭环写进 prompt |
| 拒绝目录外的危险命令 | 修改安全限速、绕过串口检查 |

## 5. 建议的仓库布局

在现有结构上只加一个薄层，不要另起框架：

```text
skills/
  README.md                 # 技能目录：一张表就够 Agent 选型
  launch-fullstack.md       # 单技能卡片
  stop-fullstack.md
  check-health.md
  probe-chassis.md
  probe-camera.md
  enter-docker.md
  ...
docs/
  Agent控制架构.md          # 本文：原则、分层、延迟、安全
  快速启动指南.md           # 人用的操作手册，继续保留
  部署调试备忘.md
playbooks/
  启动前检查.md
  串口缺失.md
  相机无画面.md
  全栈已在跑时的请求.md
state/
  current.md                # 可选：最近一次检查写出来的短状态
scripts/                    # 真正执行的技能，保持现状
```

如果希望更少目录，也可以把 `skills/` 和 `playbooks/` 都放进 `docs/agent/`。关键是**目录、卡片、剧本、原则**四类文本分开，不要继续把它们混在长手册里。

`docs/快速启动指南.md` 仍然给人看。Agent 默认先读技能目录和剧本；只有诊断或手册里才有的细节时，再去打开长文档。

## 6. 技能怎么打包

一个技能同时有两样东西：**可执行入口**和**一张卡片**。卡片是给 Agent 的 API 文档，脚本是实现。

### 6.1 脚本约定（这个仓库已经基本满足）

- 默认非交互，不要 `read -p`。
- 可重复执行：启动前清理、停止时允许进程已不在。
- 从仓库根目录调用，自己 `source config/robot.env`。
- 标准输出要能被 Agent 判断：成功/失败用明确标记，关键地址和设备路径打在最后几行。
- 长日志进 `data/logs/`，不要强迫 Agent 读完整日志才能知道成没成。
- 退出码：`0` 成功，非 `0` 失败。需要“已跳过”时，用 stdout 的稳定关键字，不要用含糊的 0。

现有 `launch_all.sh` / `check_all.sh` / `stm32_hoverboard_probe.sh` 已经接近这个标准。新技能按同样方式加，不要为 Agent 再包一层 Python 框架。

### 6.2 技能卡片建议字段

每张卡片保持一页以内：

```markdown
# 技能：启动全栈

- 入口：`./scripts/launch_all.sh`
- 何时用：人要求启动、上场、给 UE 推流，且健康检查显示全栈未在跑
- 不要用：串口 probe 失败时；已经在跑时再启动（先 `check-health`，必要时先停再启）
- 前置：在 Docker 内或已 source 环境；前后 STM32 串口存在；急停可用；轮子架空或限速仍为安全值
- 调用：`./scripts/launch_all.sh`
- 成功：退出码 0，出现 `/cmd_vel 在线`，打印 RTSP/HLS/rosbridge 地址
- 失败：缺串口会直接停；下一步看剧本「串口缺失」
- 副作用：会清已有进程再拉起
- 安全：不得在卡片外追加提高 `HOVERBOARD_COMMAND_LIMIT_RPM` 的命令
```

目录表只保留四列，让 Agent 一次读完就能选型：

| 技能 | 入口 | 一句话 | 典型触发语 |
|---|---|---|---|
| 启动全栈 | `./scripts/launch_all.sh` | 拉起底盘/相机/推流/UE 桥/GUI | 启动、上场、开车 |
| 停止全栈 | `./scripts/stop_all.sh` | 停掉本仓库拉起的服务 | 停车、关掉、停止 |
| 健康检查 | `./scripts/check_all.sh` | 看各服务是否在 | 怎么样了、健康吗 |
| 底盘探测 | `./scripts/stm32_hoverboard_probe.sh` | 查 ROS 依赖和前后串口 | 串口、底盘连上没 |
| 相机探测 | `./scripts/hikrobot_camera_probe.sh` | 查 Hikrobot/Aravis | 相机、有画面吗 |
| 进入 Docker | `./scripts/docker_run_stm32.sh` | 进入 Humble 运行时 | 进容器、隔离环境 |

复合流程优先做成**一个脚本**（现在的 `launch_all.sh` 就是），而不是让 Agent 自己按顺序调五个入口。Agent 编排只留给少见、需要看现场才能决定的组合。

### 6.3 现有脚本如何映射成第一批技能

| 技能名 | 现有入口 | 备注 |
|---|---|---|
| 进入 STM32 运行时 | `scripts/docker_run_stm32.sh` | 当前常用主环境 |
| 启动全栈 | `scripts/launch_all.sh` | 容器内执行 |
| 停止全栈 | `scripts/stop_all.sh` | |
| 健康检查 | `scripts/check_all.sh` | 状态快照的主要来源 |
| 底盘探测 | `scripts/stm32_hoverboard_probe.sh` | 启动前硬前置 |
| 相机探测 | `scripts/hikrobot_camera_probe.sh` | 无相机不应阻塞底盘时，卡片里写清 |
| 绑定 CH340 | `scripts/bind_ch341_serial.sh` | 只在剧本「串口缺失」里出现 |
| 键盘控制 | `scripts/keyboard_control.sh` | 交给人，Agent 只负责打开 |
| 打开控制台 | `scripts/open_car_gui.sh` | 同上 |
| 部署依赖 | `scripts/deploy_dependencies.sh` | 低频，不进日常对话 |
| 构建镜像 | `scripts/docker_build.sh` | 低频 |

第一批不要把 `ros2 topic pub`、改 profile、提高 RPM 做成技能。那些要么是实时控制，要么是安全变更，必须人明确要求并走文档，而不是对话里顺手做。

## 7. 文档系统怎么写给 Agent 看

给人看的手册可以按章节讲。给 Agent 看的文档要按**决策**写：先给结论，再给动作，少给背景。

建议四层，从短到长：

1. **原则（本文）**  
   谁做什么、什么能调、什么不能调、延迟策略、安全红线。Agent 每个会话读一次。
2. **技能目录**  
   只用于选型。读完应能决定“调哪一个”，而不是“再去翻手册”。
3. **剧本**  
   把反复出现的现场写成 `如果…则…否则…停止并汇报`。这是降延迟的关键，见第 8 节。
4. **长手册与项目记忆**  
   `docs/快速启动指南.md` 等继续作为人用权威来源；`.codex-memory/` 继续记录稳定事实和未完成工作。Agent 只在目录和剧本不够时再打开。

写给 Agent 的句子要用可判定的词：

- 好：`若 probe 输出缺少 /dev/ttyUSB1，执行 bind_ch341_serial.sh，再 probe 一次；仍缺则停止，不要 launch_all.sh。`
- 差：`串口有问题时先检查一下再看看能不能启动。`

原则里应写死读文档的顺序，避免每次会话都把全部 `docs/` 读进上下文：

1. 本架构文档中的安全红线和职责边界
2. 技能目录
3. `state/current.md`（若存在且不太过期）
4. 与用户意图匹配的一张卡片或一个剧本
5. 必要时才读长手册或 `.codex-memory/`

## 8. 交互原则

这些规则应同时出现在 Agent 系统提示和本文中，避免只写在聊天习惯里。

1. **只调用目录中的技能。** 用户口语再自然，也要落到某一行入口。对不上就问一句，或拒绝，不要临时发明命令。
2. **先看状态，再动手。** 默认先 `check_all.sh` 或读 `state/current.md`。全栈已在跑时，用户说“启动”应回报“已在跑”，而不是再 launch 一次。
3. **先剧本，后推理。** 有匹配剧本就按剧本走。没有剧本才允许短推理，并且推理结果不得突破安全红线。
4. **一次只做一件顶层事。** 需要组合时，用已有复合脚本。不要在一轮对话里又改配置又提速又启动。
5. **回报要可验证。** 说“启动成功”时带上退出码、关键话题、地址；说失败时带上脚本最后几行和下一步剧本。
6. **人在环的安全项必须停下来问。** 提高 `HOVERBOARD_COMMAND_LIMIT_RPM`、改串口映射、在轮子未架空时做运动测试，默认拒绝自动执行。
7. **实时运动不经 Agent。** “往前开”应打开键盘/GUI/UE 控制，或调用将来单独设计的、内部自带超时停车的短技能；禁止 Agent 循环发速度指令。
8. **中文交互，命令保持原样。** 对人用中文解释，对机器粘贴真实命令和路径。

把 Droid 一类 CLI Agent 接到车上时，建议工作目录就是仓库根，系统提示只引用上述短文档，并打开“可直接跑命令、不必逐步审批”的模式。审批适合改代码，不适合当场操作机器人；机器人的闸门应放在技能和硬件急停上，而不是放在每条 `ls` 的确认框上。

## 9. 反应时间：问题在哪，怎么压

Agent 当交互层，慢的不是底盘，而是**决策链路**：

```text
听懂话 → 读一堆文档 → 思考 → 选工具 → 执行脚本 → 读输出 → 再思考 → 回答
```

脚本本身通常是秒级；多出来的几秒到几十秒，几乎都在“重复决策”和“过长上下文”。优化目标应分层，不要幻想把 LLM 优化成 20 ms 的控制环。

| 任务类型 | 可接受延迟 | 做法 |
|---|---|---|
| 急停、松手停车 | 毫秒～几十毫秒 | 硬件 / 脚本 / 本地按键，不经 Agent |
| 已绑定的短技能（“停车”“检查”） | 大约 1 秒内开始执行 | 快路径，不思考 |
| 日常任务（“启动全栈”） | 2～8 秒到开始跑脚本 | 目录 + 剧本，短上下文 |
| 诊断（“为什么没画面”） | 十几秒可以接受 | 才允许读长文档和日志 |

### 9.1 用文档减少推理，而不是增加阅读

更丰富的情况解读文档能降延迟，前提是**短、可判定、按情况拆开**。把所有异常写进一篇长故障手册，反而更慢。

优先写这些剧本：

- 用户要启动，全栈已在跑 → 只检查并汇报，不重启
- 用户要启动，未进 Docker → 先 `docker_run_stm32.sh`，再在容器内 launch
- probe 缺后串口 → 绑定 CH340，再 probe；仍缺则停止
- 相机探测失败但人只要底盘 → 按卡片决定是否允许缺相机继续
- 用户要“看看怎么样” → 只跑 `check_all.sh`
- 用户说话含糊 → 用目录里的触发语反问一次，不要同时跑三个技能

剧本把“这种情况已经决定过了”写死，Agent 就不必每次重新权衡。

### 9.2 避免重复决策

同一会话里，同样的问题只决定一次：

- 会话开始读一次目录、原则、短状态，之后不要每轮再读全部 `docs/`。
- 刚跑过 `check_all.sh`，几十秒内不要为了“再确认”跑第二次，除非脚本失败或用户报告硬件变化。
- 把检查结果写成 `state/current.md`（时间戳、profile、串口、`/cmd_vel`、相机、推流地址）。下一轮先读它。
- 常见口语到技能的映射写进目录的“典型触发语”，避免同义句每次都当新问题。
- 复合流程收进一个脚本。Agent 决策次数从 N 降到 1，延迟和失误一起下降。

### 9.3 关闭或降级思考

对操作型 Agent，“想得漂亮”通常有害。建议按意图分档：

- **调度档（默认）：** 关思考 / 最低推理。用户话能对上目录或剧本，就直接调用。Droid / Codex / Claude Code 里选 fast、disable thinking、low reasoning。
- **诊断档：** 只有剧本未覆盖、脚本失败、或用户明确要查原因时，才提高推理，并限定只读相关卡片、日志尾部和备忘中的一节。
- **开发档：** 改驱动、改协议、改安全限速时才用强推理。那是写代码，不是开车。

具体手段：

- 系统提示写明：匹配技能后立即调用，不要先解释计划。
- 需要向人确认时，问一句可选项，不要分析三段。
- 用较小、较快的模型做日常调度；大模型留给少见故障。
- 禁止“先读完所有文档再动手”。读目录 → 动手 → 必要时再补读。

### 9.4 快路径：不要每句话都走大模型

即使主交互是 Agent，也应留一条不经过完整推理的快路径：

1. **关键词表：** `停止/急停/停车` 直接 `stop_all.sh`；`检查/状态` 直接 `check_all.sh`。可放在 Agent 外的一层极薄路由，或放在系统提示最前面。
2. **粘性模式：** 人说“接下来你只用检查，不要启动”，本会话就不再考虑 launch。
3. **预热会话：** Agent 常驻在 Docker 工作目录，文档已在上下文里。每次从冷启动读 `AGENTS.md` + 全部记忆，会把第一句拖到几十秒。
4. **工具 schema：** 若所用 Agent 支持函数调用，把技能目录做成 tool spec（名字、参数、一句话描述）。选工具比读 Markdown 更快、更稳。
5. **并行只用于只读：** 底盘 probe 和相机 probe 可以并行；启动类技能不要并行，避免抢设备和端口。

### 9.5 仍然不要优化错对象

- 把 Agent 从交互层下沉到速度环，怎么关思考都不够快。
- 为了快而让 Agent 跳过 probe 直接 launch，省几秒，换一次误动。
- 为了快而把所有日志塞进 prompt，上下文变长，反而更慢。
- 第一句回答可以短：“正在启动全栈”，脚本跑起来再补结果。人感知的等待比模型多想一轮更短。

## 10. 安全红线

这些条目应复制到 Agent 系统提示中，作为不可覆盖规则：

- 不得在未确认轮子架空/急停可用时，把 `HOVERBOARD_COMMAND_LIMIT_RPM` 从安全默认值提高。
- 底盘 probe 失败时不得 `launch_all.sh`。
- 不得为了“试试”而断开或改写急停相关路径。
- 不得循环发布 `/cmd_vel` 充当遥控。
- 不得把 `config/*.local.env` 里的密码写进文档或记忆。
- 目录外命令默认拒绝；用户明确要求改代码时，切到开发档，而不是在操作会话里改。

急停的权威顺序保持：硬件切断 TTL > 本地停止脚本/GUI 空格 > Agent 调用 `stop_all.sh`。

## 11. 落地顺序

不需要先换 Agent 产品，按现有仓库就能试：

1. 把现有 `scripts/` 收成一张技能目录，先覆盖启停、检查、两个 probe、进 Docker。
2. 给这几个入口各写一张一页卡片。
3. 写 4～6 个最高频剧本：已在跑、缺串口、只查状态、要启动、要停止、相机缺失。
4. 规定 Agent 读文档顺序和安全红线（可从本文摘到 `AGENTS.md` 的一个短节）。
5. 用现在的命令行 Agent 在车上看板：只允许调目录技能，观察延迟和误动作。
6. 把重复踩坑收成新剧本；把反复手编的三步流程收成一个新脚本。
7. 若某条口令稳定且对延迟敏感，再加关键词快路径。不要一上来做语音框架。

当前环境已经完成了第 0 步：技能能跑、文档能读、Agent 能进仓库和 Docker。缺的是把“人怎么用这些脚本”压缩成“Agent 怎么不假思索地用这些脚本”。

## 12. 和现有控制方式的关系

| 方式 | 继续保留 | 和 Agent 的关系 |
|---|---|---|
| `car_gui.py` / 键盘 | 实时驾驶 | Agent 可以打开它，不替代它 |
| UE `/U2RTopic_Command` | 场馆/展示控制 | 仍走 rosbridge；Agent 负责车上服务是否就绪 |
| `launch_all.sh` 等脚本 | 真正的任务入口 | Agent 的唯一动手面 |
| 本文 + 技能目录 + 剧本 | 新增 | 把脚本从“给人敲”变成“给 Agent 调” |

UE、GUI、Agent 可以并存。Agent 不是新的实时总线，只是把原来由人完成的任务级操作，改成对话完成。
